# 배포와 캐시 — 왜 이렇게 되어 있는가

`vercel.json` 은 JSON 이라 주석을 못 단다. 한 번 `"//"` 키로 설명을 적었다가
**배포가 통째로 실패했다** — Vercel 은 `vercel.json` 을 스키마로 엄격하게 검사하고,
`headers` 항목에는 `source` · `headers` · `has` · `missing` 말고 다른 키가 있으면
빌드에 들어가기도 전에 거절한다. 그때 Vercel 은 **직전 배포판을 그대로 계속 서빙**하므로,
화면에서는 "고친 것이 반영되지 않는다"로만 보인다. 캐시와 구별이 안 된다.

그래서 설명은 여기 적는다.

---

## 왜 `?v=` 를 손으로 올리지 않는가

`?v=` 는 원래 손으로 올리는 숫자였다(183 → 184 → 185). 세 번 올리고도 반영이
안 되는 일이 났다. 이유가 둘이었다.

1. **그 번호를 들고 있는 파일이 `index.html` 자신이다.** 브라우저가 `index.html` 을
   캐시에 물고 있으면 번호를 올렸다는 사실 자체가 전달되지 않는다. 옛 HTML 이
   옛 `?v=` 를 부르고, 그 URL 은 이미 캐시에 있으니 끝까지 옛 코드가 돈다.
2. **손으로 하는 일은 빠지면 그만이다.**

지금은 `tools/build-site.sh` 가 배포마다 **커밋 해시로 찍는다**
(`VERCEL_GIT_COMMIT_SHA` → `GITHUB_SHA` → `git rev-parse` → 시각 순으로 고른다).
`game/assets/sprites.js` 는 제 `<script>` 태그의 물음표 뒤를 그대로 물려받아
그림 URL 에도 붙이므로(`_ver`), 이 한 번으로 스크립트·CSS·그림이 같이 따라온다.

`sed` 만 쓴다. 처음에는 `perl` 로 썼는데, 빌드 이미지에 perl 이 없으면
`set -e` 가 빌드를 실패시키고 — 그러면 위와 똑같이 **옛 배포판이 그대로 남는다**.
`sed -i` 는 GNU/BSD 문법이 갈리므로 임시 파일로 돌린다.

찍히지 않은 자리가 남으면 빌드를 **일부러 실패시킨다**. 안 찍힌 판이 1년 캐시되는
것이 제일 나쁘다.

## 캐시 규칙

| 무엇 | 얼마나 | 왜 |
|---|---|---|
| `/play`, `/play/*.html` | 매번 확인 | `?v=` 를 들고 있는 파일. 이게 쟁여지면 나머지가 다 소용없다 |
| `/play/*.js`, `/play/*.css` | 1년 immutable | 배포마다 URL 이 달라지므로 옛것이 나올 길이 없다 |
| `/play/assets/*.png` 등 | 1년 immutable | 위와 같다(`_ver`) |
| `/play/assets/manifest.json` | 매번 확인 | `?v=` 가 안 붙는다 — `sprites.js` 가 직접 fetch 한다 |
| `/play/version.json` | `no-store` | "지금 도는 판이 뭐냐"고 묻는 자리 |

규칙끼리 겹치면 어느 쪽이 이기는지가 플랫폼 사정에 달리게 된다. 그래서 `source`
패턴을 **서로 겹치지 않게** 갈라 두었다(확장자를 하나하나 적은 것도 그래서다).

## 그래도 옛 HTML 이 오면

`game/index.html` 안에 자가 점검이 들어 있다. `version.json` 을 `no-store` 로
물어보고 제가 든 판과 다르면 주소 뒤에 `?b=<판>` 을 붙여 **딱 한 번** 새로 받는다.
같은 판으로 두 번 시도하지 않게 세션에 적어 둔다 — 무한 새로고침이 제일 나쁘다.
`file://`(zip)에서는 물어볼 데가 없으므로 건너뛴다.

## 지금 도는 판을 어떻게 보는가

타이틀 화면 구석에 적혀 있다 — `v1.0.5 · 4620896`.
`game/` 을 직접 열었을 때는 `v1.0.5 · 개발판`.
서버에 직접 물어보려면 `/play/version.json`.

셋 중 무엇이 문제인지(캐시 / 배포 실패 / 코드)를 구별할 데가 여태 없어서 붙였다.
