## 0. 목표와 원칙

**가장 중요한 목표**는 "Ashfall을 만들기 위한 코드"와 "게임을 만들기 위한 엔진 코드"를 분리하는 것이다. 엔진은 다른 2D 타일 게임에서도 다시 쓸 수 있어야 한다.

같이 하는 일:

- **파일·모듈 분리:** 큰 파일을 역할별 모듈로 나눈다. 순환 의존은 없앤다.
- **TypeScript 기반:** 빌드 환경을 만들고, 엔진 핵심부터 점진적으로 옮긴다.
- **다국어:** 한국어·영어·일본어·중국어 간체·독일어·스페인어 6개 언어를 지원할 수 있는 구조를 만든다.
- **모바일:** 터치 입력, 화면 비율, UI 크기를 엔진의 입력·화면 계층과 연결한다.
- **Docker:** 개발·실행 환경을 재현할 수 있게 한다. 지금의 로컬·브라우저·zip 실행 방식은 유지한다.

원칙(사용자 지시 그대로):

1. 게임플레이와 콘텐츠를 임의로 바꾸지 않는다. 수치·확률·문구·생성 결과는 그대로 둔다.
2. 필요 이상의 리팩터링은 하지 않는다.
3. **기존 기능을 깨뜨리지 않는 것이 최우선이다.**
4. 목적은 엔진화다. 파일을 여러 개로 나누는 것 자체가 목적이 아니다.

이 저장소에서 추가로 지킬 것:

- **CLAUDE.md §1의 절대 규칙은 그대로 유효하다.** 타일 번호는 맨 끝에만 붙이고, 타일은 `world.set()`으로만 바꾸고, 세이브 모양을 바꾸면 `SAVE_UPGRADES`에 한 칸을 더하고, 좌표에는 `SHIFT`와 `SX`/`SY`를 쓴다.
- **세계 생성은 바이트 단위로 같아야 한다.** 난수를 부르는 순서가 하나라도 바뀌면 같은 씨앗이 다른 세계가 된다. 기존 세이브는 타일을 저장하므로 깨지지 않지만, "씨앗 → 세계" 재현성이 깨진다. 모든 단계에서 §6-1의 해시 대조로 막는다.
- **zip 빌드의 `file://` 실행을 유지한다.** 크롬은 `file://`에서 `<script type="module">`과 `fetch`를 막는다. 그래서 산출물은 **클래식 스크립트 번들(IIFE)**이어야 한다(§3-4).

### 1-2. 불러오는 방식

`index.html`이 클래식 `<script>` 13개를 순서대로 부른다. 모두 **전역 스코프를 공유**하고, 모듈이나 import는 없다.

```
util → data → world → tileart → itemart → titlebg → sprites-manifest → sprites
     → entity → factory → ui → music → game
```

전역 이름은 약 330개다(data 170 · entity 40 · world 28 · util 26 · music 20 · game 16 …).

### 1-6. 이미 엔진처럼 되어 있는 것 (살려서 쓴다)

- **입력이 액션 기반이다.** `KEY_ACTIONS`와 `keysFor`/`held`/`isKey`가 있고 키도 다시 매길 수 있다. 터치를 붙이기 좋은 자리다.
- **세이브 계층.** `SaveStore`(IndexedDB·gzip·서명, localStorage 대체)와 `SAVE_UPGRADES` 마이그레이션 사슬이 있다.
- **애셋 매니페스트 파이프라인.** `manifest.json` → `sprites-manifest.js`, 스프라이트 키 규칙이 있다.
- **데이터 주도 표.** 타일·아이템·몹·제작법·장이 전부 `data.js`의 표다.
- **결정론적 생성.** 씨앗 → `RNG`, 크기 배수는 `SX`/`SY`.
- **오디오 계층.** `Music`·`Sfx`·`SfxLoop`·`Ambient`는 게임 이름을 거의 모른다.
- **화면 비율.** `resize()`가 창 크기와 DPR(2 상한)을 따른다.

### 1-7. 엔진화를 막는 것

1. **전역 `G` 하나가 곧 게임 상태이자 서비스 창구다.** 엔티티·UI·팩토리가 `G.player`, `G.parts`, `G.sfx`, `G.toast` 같은 것을 직접 부른다.
2. **`World`에 타일맵 엔진과 Ashfall 생성기가 섞여 있다.** 한 클래스 4,900줄이다.
3. **렌더가 한 덩어리다.** 캔버스 호출 671번이 `game.js` 안에 있고, 타일 그리기·원경·몹·연출이 한 함수 흐름에 붙어 있다.
4. **문구가 코드에 박혀 있다.** 한국어 리터럴이 약 3,900개이고, 조사 함수(`josa` 외 4종)가 문장 조립에 끼어 있다.
5. **모듈 시스템과 빌드가 없다.** `package.json`, 번들러, 타입 검사, 린트, 테스트 러너가 없다. 파이썬 도구와 bash 빌드만 있다.

## 2. 목표 구조

### 2-1. 층과 의존 방향

```
┌──────────────────────── games/ashfall ────────────────────────┐
│ content/  (data 표 · 대사 · 장 · 몹 · 아이템 · 애셋 목록)        │
│ world/    (Ashfall 생성기 · 마을 · 유적 · 바다)                 │
│ systems/  (전투 · 농사 · 낚시 · 공장 · 유적 맥박 · 운석 · 진행 …) │
│ ui/       (가방 · 제작 · 상점 · 기계 … 패널)                     │
│ render/   (원경 · 하늘 · 몹 연출 등 게임 고유 그리기 훅)           │
│ scenes/   (title · play)          main.ts (조립)                │
└───────────────▲──────────────────────────────────────────────┘
                │ import 만 (역방향 금지)
┌───────────────┴──────────── engine/ ──────────────────────────┐
│ core/     loop · time · events(버스) · app 컨텍스트 · rng · math │
│ platform/ viewport · DPR · 전체화면 · 방향 · 가시성               │
│ input/    액션 매핑 · 키보드 · 마우스 · 포인터/터치 · 가상 패드     │
│ render/   캔버스 · 카메라 · 스프라이트 · 타일맵 렌더 · 아틀라스     │
│           · 연결 타일(CONN) 틀 · 조명 합성 · 파티클               │
│ tilemap/  타일 배열 · set/get · 벽지 · 조명 · 유체 · RLE 직렬화   │
│ entity/   엔티티 기반 · AABB 물리 · 타일 충돌 · 투사체             │
│ scene/    씬 스택(title/play/pause/modal)                       │
│ ui/       패널 틀 · 툴팁 · 드래그 · 슬롯 그리드 · 모달 · 토스트     │
│ audio/    BGM · SFX · 루프 · 환경음 · 잠금 해제                    │
│ save/     저장소(IDB·gzip·서명) · 슬롯 · 마이그레이션 사슬          │
│ assets/   매니페스트 · 로더 · 발 여백 측정                          │
│ i18n/     로케일 · 메시지 포맷 · 언어별 문법 훅 · 폰트 스택           │
└───────────────────────────────────────────────────────────────┘
```

규칙:

- **`engine/`은 `games/` 아래를 절대 import하지 않는다.** CI에서 기계적으로 검사한다(§6-4).
- 엔진은 게임을 **훅·레지스트리·설정 객체**로만 안다. 예: 타일 정의 표, 입력 액션 목록, 세이브 스키마 버전과 마이그레이션, 로케일 묶음은 게임이 엔진에 등록한다.
- 게임 쪽에서도 `content/`는 순수 데이터로 둔다. 다른 게임 모듈을 import하지 않는다(현재 `data → world`·`data → entity` 역참조는 끊는다).

### 2-2. 전역 `G`를 어떻게 다루나

한 번에 없애지 않는다. 다음 순서로 **좁혀 간다**.

1. `G`를 `AshfallApp`(게임 인스턴스)으로 이름만 감싼다. `window.G`는 디버그용 별칭으로 남긴다(`?debug=` 도구와 기존 콘솔 확인 방식이 이것에 기댄다).
2. 엔진 서비스를 `app.engine = { input, audio, save, assets, events, i18n, viewport }`로 모은다. `G.sfx(...)`는 `engine.audio.sfx(...)`로 가는 얇은 전달 함수로 남긴다.
3. `entity.js`·`ui.js`의 `G.` 참조 474번을 **용도별**로 분류한다(상태 읽기 · 효과음 · 파티클 · 토스트 · 드롭 생성 …). 그 결과로 컨텍스트 인터페이스를 정의한다(`EntityContext`, `UiContext`). 호출부는 기계적으로 바꾼다.
4. 새 코드는 `G`를 쓰지 않는다. 옛 코드의 `G`는 컨텍스트 인터페이스 뒤로 숨긴다.

### 2-3. 엔티티

전면 ECS로 다시 쓰지 않는다. 필요 이상의 리팩터링이고, 동작이 바뀔 위험이 크다. 대신:

- 엔진 `Entity` 기반: 위치·속도·AABB, 타일 충돌(`tilemap` 질의), 중력·발판, 수명.
- 공통 기능은 **가벼운 컴포넌트/믹스인**으로 뺀다: 헤엄, 넉백, 상태 이상, 스프라이트 애니메이션 선택.
- `Player`·`Enemy`(AI `ai: 'walker'…`)·`Pet`·`Bomb`·`Drop`은 게임 쪽 클래스로 남아 엔진 기반을 상속한다.

### 2-4. 타일맵과 월드

- `engine/tilemap`: 타일·벽지 배열, `get/set/solid/platform`, 탐험·조명 갱신 훅, 유체 시뮬레이션 틀(타일 종류 표는 게임이 준다), RLE 직렬화.
- `games/ashfall/world`: `generate()`와 그 아래 모든 것(바이옴·동굴·유적·마을·바다·섬·나무). **`World extends TileMap`**(상속 — §8-4 결정).
- **CLAUDE.md의 모든 월드 규칙은 게임 쪽 문서로 그대로 따라간다**(`SHIFT`·`SX/SY`·`sealLiquids` 순서 등).

### 2-5. 렌더

- 엔진: 캔버스·DPR, 카메라, 화면 안 타일 순회, 아틀라스 블릿, **연결 타일 틀**(`CONN`/`drawConn`의 캐시·이웃 마스크 구조), 조명 합성, 스프라이트 그리기(발 여백), 파티클, 텍스트 그리기(i18n 폰트 스택).
- 게임: 타일 질감·색(`ART`), 원경·하늘·해·운석, 몹·보스 연출, 문·기계 그림, 미니맵 색.
- 순서는 **렌더 파이프라인 단계 목록**으로 정의한다(하늘 → 원경 → 벽지 → 타일 → 엔티티 → 연출 → 조명 → UI 캔버스). 게임은 각 단계에 그리기 함수를 등록한다.

## 3. 모듈 분리와 TypeScript

### 3-1. 디렉터리 (제안)

```
src/
  engine/…              (§2-1)
  games/ashfall/…
  main.ts               게임 조립 · 부팅
game/                   ← 지금처럼 "이 폴더만 올리면 도는" 실행 폴더
  index.html · css/ · assets/
  js/ashfall.js         ← 빌드 산출물(IIFE 번들 1개 + 소스맵) — **저장소에 커밋한다**(§8-1)
tools/ · docs/ · site/ · launchers/
```

### 3-2. 옮기는 방법 — 한 번에 다 바꾸지 않는다

1. **0단계: 파일 그대로, 번들만.** 지금 JS 13개를 `src/legacy/`로 옮기되 **내용은 그대로 둔다.** esbuild로 순서대로 이어 붙인 IIFE 하나를 만든다(전역 공유가 그대로 유지된다). 산출물로 게임이 똑같이 도는지 §6으로 확인한다.
2. **1단계: 파일마다 ES 모듈로.** `export`/`import`를 명시하고, 전역이 필요한 것만 `window`에 싣는다. 이때 §1-3의 역의존을 끊는다.
3. **2단계: 엔진 모듈을 떼어 낸다**(§7 순서). 뗀 모듈부터 `.ts`로 바꾼다.
4. 게임 쪽 JS는 `allowJs` + 필요한 곳만 `// @ts-check`로 오래 공존한다.

### 3-3. TypeScript 설정

- `tsconfig.json`: `strict: true`는 `src/engine/**`에만 건다. 게임 쪽은 `allowJs`·`checkJs: false`로 시작한다. `noEmit`으로 타입 검사만 하고, 산출은 esbuild가 한다(tsc는 검사 전용).
- **데이터 표 타입**을 먼저 만든다. 콘텐츠를 바꾸지 않고도 오타·빠진 필드를 잡는다: `TileDef`·`ItemDef`·`EnemyDef`·`RecipeDef`·`ChapterDef`·`MachineDef`. 예: 새 아이템에 그림이 없으면 타입이나 검사 스크립트가 잡는다(CLAUDE.md §1-6 재발 방지).
- 타일 id는 `const enum`이 아니라 **지금 숫자 그대로**인 `as const` 객체로 둔다. 세이브가 숫자를 담는다.

### 3-4. 빌드 도구

- **esbuild**: 빠르고 설정이 적다. IIFE 출력과 소스맵을 낸다. `file://` 실행이 된다.
- `package.json` 스크립트: `dev`(watch + 정적 서버), `build`, `typecheck`, `lint`, `test`, `check`(아래 모두).
- **"고치고 새로고침" 흐름을 지킨다.** `npm run dev`가 watch 빌드를 돌린다.
- **산출물은 커밋한다**(§8-1). 그래서 `game/`만 받아도 빌드 없이 돈다. 대신 CI에서 `npm run build` 결과가 커밋된 `game/js/ashfall.js`와 같은지 검사한다. 소스만 고치고 번들을 안 올리는 실수를 막기 위해서다.
  커밋 전 훅(`npm run build`)을 권한다.
- 기존 파이썬 도구(`sync-manifest.py`·`sizediag.py`·`ruindiag.py` …)와 `build.sh`/`build-site.sh`는 유지한다. `build-site.sh`에는 번들 단계만 더한다. **"죽지 않는다" 원칙**(빌드가 실패하면 Vercel이 직전판을 조용히 계속 서빙한다)도 그대로 따른다.

## 4. 다국어 (6개 언어)

### 4-1. 범위

| 출처 | 양(실측) | 처리 |
|---|---|---|
| `data.js` 표(아이템·몹·장·대사·업적·도움말…) | 한국어 리터럴 약 3,270개 | **id 기반 키**로 뽑는다: `item.<id>.name`, `item.<id>.desc`, `chapter.<n>.title` … |
| `game.js` 토스트·안내 | 약 290개 | 의미 키: `toast.anvil.break` … |
| `ui.js` 패널 문구 | 약 200개 | 의미 키 |
| `index.html` 마크업 | 한국어 198줄 | `data-i18n` 속성 + 부팅 때 채우기 |
| 기타(world·factory·entity·util) | 약 150개 | 의미 키 |

### 4-2. 구조

- `src/games/ashfall/locales/{ko,en,ja,zh-Hans,de,es}/*.json`. 한국어가 **원본(source of truth)**이다.
- 엔진 `i18n`:
  - `t(key, params)` 함수.
  - 대체 사슬: 지정 언어 → 영어 → 한국어 → 키.
  - 언어 전환: 설정 `SET_KEY`에 `lang`을 더하고, 기본값은 `navigator.language`로 정한다.
  - 숫자·날짜는 `Intl`로 쓴다(현재 `fmt`).
- **메시지 포맷**은 ICU 부분집합으로 한다: `{name}` 치환, `{n, plural, …}`, 그리고 선택형 `{x, select, …}`.
- **언어별 문법 훅**
  - 한국어 조사: `{name|을}` → 받침에 맞춰 을/를. 지금 `util.js`의 `josa`·`iga`·`eulreul`·`eunneun`·`josaRo`를 **한국어 포맷터 플러그인**으로 옮긴다. CLAUDE.md의 "'이(가)'처럼 둘 다 적지 말 것" 규칙을 여기서 강제한다.
  - 독일어·스페인어: 복수, 그리고 필요한 곳의 성·격.
  - 영어: 복수와 관사.
  - 일본어·중국어: 복수가 없다. 띄어쓰기가 없어서 줄바꿈 규칙이 다르다.
- **세이브에는 문구를 넣지 않는다.** 지금도 대부분 id를 담는다. 확인된 예외는 `saveHead`의 기본 이름 `'이름 없는 모험가'`다. 이것은 **불러올 때 번역**한다(저장값이 비어 있으면 키로 표시). 이 확인을 1순위 검사로 둔다.

### 4-3. 폰트와 글자 렌더링

- UI(DOM)는 `html[lang]`마다 폰트 스택을 둔다.
  - ko: Pretendard 계열(지금 그대로)
  - ja: Noto Sans JP
  - zh-Hans: Noto Sans SC
  - de/es/en: Latin 스택
- 캔버스 글자는 `c.font`를 쓰는 7곳(피해 숫자·이름표·알림)을 **엔진 텍스트 함수 하나**로 모으고, 로케일 폰트 스택을 쓴다.
- CJK 웹폰트는 크다. **해당 언어를 고를 때만** 불러오거나, 쓰는 글자만 서브셋으로 만들어 넣는다.
- 오프라인 zip을 위해 폰트 파일은 애셋에 넣는다. CDN에 기대지 않는다.
- **글 길이:** 독일어는 한국어보다 1.5~2배 길다. 버튼·탭·툴팁은 줄바꿈과 말줄임 규칙을 CSS로 준다. 고정 폭(`.keybtn{min-width:132px}` 등)을 점검한다.
- **줄바꿈:** ja·zh는 `word-break`/`line-break: strict`를 쓴다. ko는 지금 그대로 `keep-all`이다.

### 4-4. 진행 방식

1. 추출 스크립트를 만든다(`tools/i18n-extract`). 한국어 리터럴을 찾아 키 후보와 원문 표를 만든다. 표에 있는 문구는 **자동**으로, 코드의 문장은 **사람이 검토**해서 옮긴다.
2. **ko만으로 먼저 완성한다.** 키로 바꾼 뒤에도 화면이 글자 하나 다르지 않아야 한다(§6-2 스크린샷 대조).
3. 그 다음 en → ja·zh-Hans·de·es 순으로 **Claude가 번역한다.** 검수는 **Grok**이 한다(§8-5).
   - 먼저 **용어집**(`locales/glossary.csv`: 바이옴·장 이름·고유명사·몹·재료 — 언어별 확정 표기)을 만들고 검수받는다.
   - 검수용 시트를 낸다: 언어마다 `tools/i18n-review/<lang>.csv` — 키 · 한국어 원문 · 번역 · 쓰이는 자리(패널·토스트·대사) · 글자 수 상한 · 자리표.
   - Grok 수정본을 다시 반영하는 스크립트를 둔다(키 기준 병합 · 자리표 검사).
4. 검사 도구를 만든다: 빠진 키, 안 쓰는 키, 치환 자리표 불일치, 다른 언어에 한국어가 남은 것.

## 5. 모바일 · Docker

### 5-1. 모바일

- **입력:** 엔진 input에 포인터 이벤트(`pointerdown/move/up`)를 붙인다. 가상 조작을 만든다.
  - 왼쪽 가상 스틱 → 이동 액션
  - 점프·대시 버튼
  - 핫바 탭
  - 화면 탭·길게 누르기 → 채굴·공격·설치(조준점은 탭 위치)
  - **모두 기존 `KEY_ACTIONS` 액션으로 들어가게** 해서 게임 코드는 입력 장치를 모르게 한다.
- **대상(§8-6):** **폰은 가로 화면만, 그리고 태블릿.** 폰 세로 화면에서는 "가로로 돌려 주세요" 안내만 띄운다. 태블릿은 가로를 기준으로 맞추고, 세로에서도 깨지지 않게만 한다.
- **화면:** `viewport` 메타에 `viewport-fit=cover`를 쓰고 안전 영역(`env(safe-area-inset-*)`)을 반영한다. `resize()`의 DPR 상한은 모바일 발열·배터리를 보고 조절한다.
- **UI 크기:** 패널·슬롯 크기를 CSS 변수(`--ui-scale`)로 준다. 터치 대상은 최소 44px로 한다. 탭 단추 줄(`#tabbar`)은 이미 있다.
- **호환성:**
  - iOS Safari: IndexedDB 동작, 오디오 잠금 해제(`music.js`의 `pointerdown` 1회 시작이 이미 있다), 100vh 문제.
  - 안드로이드 크롬: 전체화면 API.
  - 저사양: 파티클·조명 품질 설정.
- **성능 예산:** 중급 폰 60fps. 월드 생성 시간(지금 소형 3.1s)은 로딩 표시로 흡수한다.

### 5-2. Docker

- `Dockerfile` 다단계:
  1. `node:lts`: `npm ci` → typecheck → build.
  2. `python:3`: 매니페스트 sync·검사 도구.
  3. `nginx:alpine`: `game/`(또는 `site/`)을 서빙한다.
- `docker-compose.yml`: `dev` 서비스(소스 마운트 + watch + 정적 서버, 포트 8000)와 `site` 서비스(배포판과 같은 산출물).
- Playwright 검사를 Docker 안에서 돌린다(공식 이미지 `mcr.microsoft.com/playwright`). §6의 회귀 검사를 누구 컴퓨터에서든 같게 돌리기 위해서다.
- **기존 방식을 유지한다:** `python3 -m http.server`, `index.html` 더블클릭(zip), Vercel·Pages 워크플로.

## 6. 검증 — 단계마다 통과해야 다음으로 간다

1. **세계 생성 해시:** 씨앗 d1·d3 × 크기 s·m·l의 타일·벽지 RLE 해시가 착수 전 기준값과 **바이트 단위로 같아야** 한다. `sizediag.py`의 겹침 0 · 세계 밖 0, `ruindiag.py`의 유적 통행도 확인한다.
2. **스크린샷 대조:** Playwright로 디버그 주소 9개(`docs/debug-urls.md`)와 타이틀·새 게임 창을 고정 시각·고정 씨앗으로 찍는다. 기준 이미지와 비교한다(허용 오차 작게, 애니메이션 프레임 고정). 다국어 단계의 ko 화면은 **글자까지 같아야** 한다.
3. **동작 스크립트:** 새 게임 → 몇 초 이동·채굴·설치 → 저장 → 다시 불러오기 → 상태가 같은지(위치·가방·타일). 옛 세이브(v7·v8, localStorage·IDB 둘 다)를 불러오는 것도 확인한다. 강화·문·공장(`?debug=factory` 12초 가동) 같은 최근 기능도 스크립트로 확인한다.
4. **의존 방향:** `dependency-cruiser`(또는 esbuild metafile 스크립트)로 `engine/** → games/**` import가 0인지, 순환이 0인지 CI에서 검사한다.
5. **빌드·실행:** `npm run check` 통과(typecheck·lint·test·build). `file://`로 zip 산출물을 열어 콘솔 오류 0. Docker `dev`·`site` 기동.
6. **성능:** 같은 장면의 프레임 시간이 착수 전보다 나빠지지 않을 것(±5%). 번들 크기를 기록한다.

4번(상속)을 고른 근거:
- 타일 접근 `get/set/solid`는 **260곳 넘게** 불린다. 그중 182곳이 `world.js`의 생성 코드이고, 나머지는 game 50 · tileart 19 · entity 9 · factory 3이다.
- 생성과 렌더의 가장 뜨거운 경로라서, 합성(`this.map.get`)으로 가면 호출부 260곳을 바꾸거나 한 번 더 건너뛰는 위임 함수가 생긴다.
- 상속이면 호출부가 **한 곳도 바뀌지 않는다.** V8이 단형(monomorphic) 메서드 호출을 그대로 인라인하므로 성능도 지금과 같다.
- `world.serialize()` 세이브 스키마도 그대로다. 엔진 `TileMap`의 필드 이름(`tiles`·`walls`·`explored`…)은 지금 `World`의 것을 그대로 쓴다.
- 합성이 주는 이점(한 게임에 타일맵 여러 개)은 지금 필요가 없다. 필요해지면 `TileMap`을 따로 만들어 쓰면 된다.
